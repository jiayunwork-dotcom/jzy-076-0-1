化工工艺组算精馏塔选型的时候，总要先过一遍简捷计算：最小回流比是多少、理论上最少要几块板、给定实际回流下逐板浓度怎么变，这些数手算或者拿 Excel 摆公式很容易在精馏段和提馏段两条操作线上抄错系数，两段用的组成定义一旦对不齐，算出来的板数就会跟着漂。想做一个常驻的二元精馏简捷核算服务，把这套图解法收进后端，一次接口调用把这些数直接算清楚。

服务收进料组成、馏出液与釜液的目标组成、进料热状态（用 q 值描述）、相对挥发度这几个量。先做物料闭合校验：由总进料量和这几个组成反推馏出液与釜液流量，两者之和必须等于进料量，组分衡算的残差要控制在极小容差内，闭合不上直接报错。组成关系上还要求馏出液组成大于进料组成、进料组成大于釜液组成，顺序不对也报错；相对挥发度小于等于一时直接答复「无法分离」，不需要继续算下去。

核算本体分三块。第一块用 Fenske 方程算全回流下的最少理论板数，作为其他工况的参照基准。第二块用 Underwood 方法算最小回流比。第三块是逐板阶梯计算：给定一个实际回流比（且必须大于最小回流比，否则报「回流不足」而不是陷进死循环），从馏出液组成出发，在平衡曲线与操作线之间交替求交点，直到组成降到釜液目标以下为止，每一步阶梯对应一块理论板，把每板的液相组成也一并记下来。这里精馏段操作线和提馏段操作线必须共用同一套相平衡关系式，提馏段操作线由进料热状态和物料衡算确定，不能精馏段和提馏段各自维护一份对不上的平衡曲线。

几条关系要用自动化测试锁住：任意一组合法输入，物料衡算残差都要在容差内；把回流比调到全回流（数值上取一个足够大的回流比逼近），逐板算出的理论板数应当逼近 Fenske 给出的最少板数，允许因为阶梯是离散取整而有一板的误差，但不能相差更多；给同一组分离目标，把实际回流比调大之后，达到目标所需的理论板数不能反而增加，这个单调关系要能在多组回流比下验证；回流比恰好等于或低于最小回流比时必须报错，不能继续跑出一个看似正常的板数；进料热状态改变时提馏段操作线的斜率要跟着变，但物料衡算的闭合关系不受影响。

明确的边界：组成不在零到一之间、进料量非正、相对挥发度非正这些输入都要拒绝并给出结构化的错误说明。这套服务只通过 HTTP 对外提供最小回流比、最少理论板数、逐板阶梯结果这几项核算，调用方传结构化参数拿结构化结果，不需要网页、不需要流程图编辑器之类的界面。

技术栈选 Java 17，框架用 Spring Boot。请把物料衡算、Fenske 与 Underwood 计算、逐板阶梯迭代、HTTP 接口按职责拆成独立的模块，平衡关系式只在一处定义并被精馏段与提馏段共同引用，不允许出现两份互相矛盾的实现。构建阶段选用带 JDK 17 的 Maven 官方镜像编译出可执行包，运行阶段换到瘦身后的 JRE 17 镜像加载这个包，两阶段分开写进同一份能一次构建成功的 Dockerfile，把物料闭合、全回流逼近 Fenske、回流增大板数不升、低于最小回流报错这些判据写成自动化测试留在仓库里。
